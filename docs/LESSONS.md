# LESSONS — บทเรียนจากการสร้างโปรเจ็คนี้

> **เขียนทันทีที่จับได้ ห้ามรอไปสรุปตอนจบ** — พอ context ถูกย่อ รายละเอียดที่ทำให้บทเรียนมีค่าจะหายไปหมด
>
> นับเป็นบทเรียนเมื่อ **โปรเจ็คอื่นก็จะโดนกัดแบบเดียวกัน** · พิมพ์ผิดไม่นับ
>
> ช่อง **เจ้าของกฎ** ไม่ใช่งานเอกสาร — มันคือสิ่งที่ทำให้ตอนจบ build เสนออัปเดตสกิลได้ทันที
> โดยไม่ต้องมานั่งรื้อความจำว่าเกิดอะไรขึ้นบ้าง

## ปุ่มสีเหลืองหมวกเซฟตี้ที่ใส่ตัวหนังสือขาวแล้วอ่านไม่ออก

- **สาเหตุจริง:** สีเดียวถูกใช้สองหน้าที่ที่ต้องการค่าคนละแบบ — เป็น *สีตัวหนังสือ*
  บนพื้นขาว กับเป็น *สีพื้น* ที่มีตัวหนังสือขาวทับ · เหลืองที่สว่างพอจะรู้สึกเป็นเหลือง
  จะสว่างเกินไปเสมอสำหรับหน้าที่หลัง
- **หลักฐาน:** `#D97706` ใต้ตัวหนังสือขาว = **3.18:1** (ต้องการ 4.5:1) · ขยับเป็น `#B45309` ได้ 5.02:1
  · น้ำเงิน `#1D4ED8` ได้ 6.70:1 ทำหน้าที่ได้ทั้งสองอย่างด้วยค่าเดียว
- **กฎกันซ้ำ:** แยก `--brand` (ตัวหนังสือ) ออกจาก `--brand-solid` (พื้น) เสมอ และ**วัด ไม่ใช่กะ** —
  โทนที่อิ่มตัวสูงอย่างเหลือง/ส้ม/เขียวมะนาว จะต้องใช้คนละค่าเกือบทุกครั้ง ส่วนน้ำเงิน/ม่วงเข้ม มักใช้ค่าเดียวได้
- **เจ้าของกฎ:** `thai-admin-page-kit`

## เงาสีแบรนด์บนพื้นเข้ม กลายเป็นแสงเรืองไม่ใช่ความสูง

- **สาเหตุจริง:** ตอนเปลี่ยนพาเลตต์ เผลอเปลี่ยนสีเงาตามสีแบรนด์ไปด้วย
  (`rgb(0 0 0 / .32)` → `rgb(16 40 100 / .35)`) · บนโหมดสว่างพอมองผ่านได้
  แต่บนพื้นกรมท่าเข้ม เงาน้ำเงินไม่ต่างจากพื้นพอที่จะอ่านเป็นระยะห่าง มันอ่านเป็นแสง
- **หลักฐาน:** hook `dark-glow` จับได้ที่ `docs/design/demo.html:211`
- **กฎกันซ้ำ:** เงายกระดับใช้สีกลางเสมอ (`rgb(0 0 0 / …)`) · การเปลี่ยนพาเลตต์
  ห้ามลามไปแตะโทเคนเงา — เงาไม่ใช่สีแบรนด์
- **เจ้าของกฎ:** `thai-admin-page-kit`

## ยอดรวมใน mockup ไม่ตรงกับผลบวกของแถวที่แสดงอยู่ข้างบนมันเอง

- **สาเหตุจริง:** เขียนยอดรวมด้วยมือตอนร่าง แล้วรายการย่อยถูกแก้ทีหลังโดยไม่ได้บวกใหม่
- **หลักฐาน:** เขียน `฿3,190` ไว้ 3 ที่ แต่ผลบวกจริงของ 5 คนที่คิดค่าแรงรายวันคือ **฿2,460**
  (550 + 750 + 210 + 420 + 530) · เจอตอนเขียน JS ให้ปุ่มติ๊กคำนวณจริง
- **กฎกันซ้ำ:** ตัวเลขรวมใน mockup และใน seed **ต้องคำนวณจากแถวที่แสดงจริง** ไม่ใช่พิมพ์เอา ·
  ถ้า mockup โชว์สองตัวเลขที่ขัดกัน คนดูจะเลิกเชื่อทั้งหน้า ไม่ใช่แค่ตัวเลขนั้น
- **เจ้าของกฎ:** `kp-design-brainstorm` (mockup) · `kp-seed-and-reset` (seed)

## ต้นทุนค่าแรงถูกนับสองรอบ เพราะ "จ่ายเงิน" กับ "ต้นทุน" ถูกปนเป็นเรื่องเดียวกัน

- **สาเหตุจริง:** ระบบบันทึกทั้งการลงชื่อเข้างาน (ต้นทุนเกิด) และการจ่ายเงิน
  (เบิกล่วงหน้า + ปิดรอบจ่าย) แต่ทั้งคู่ถูกวาดเป็นแถวสีแดง "รายจ่าย" เหมือนกัน
  ทั้งที่การจ่ายเงินเป็นการ*ล้างหนี้ที่เกิดไปแล้ว* ไม่ใช่ต้นทุนก้อนใหม่
- **หลักฐาน:** สมพงษ์ 6 วัน × ฿550 = ต้นทุน ฿3,300 · เบิก ฿1,000 + ปิดรอบ ฿2,300 = เงินสดออก ฿3,300
  ถ้านับทั้งสองฝั่งเป็นรายจ่ายจะได้ ฿6,600 คือสองเท่าของความจริง
- **กฎกันซ้ำ:** แอปการเงินใด ๆ ที่มีทั้ง *สิ่งที่เกิดขึ้นแล้ว* (accrual) และ *เงินที่ออกจริง* (cash)
  ต้องเลือกว่าตัวไหนคือ "รายจ่าย" ตั้งแต่ตอนออกแบบ แล้วให้อีกตัวมีป้ายกำกับของตัวเอง —
  ตัดสินตอนเขียนโค้ดแล้วจะสายเกินไป เพราะข้อมูลถูกบันทึกผิดไปแล้ว
- **เจ้าของกฎ:** `kp-design-brainstorm`

## public signup เปิดอยู่ในแอปที่ไม่มีหน้าสมัครสมาชิก

- **สาเหตุจริง:** Supabase เปิด signup ไว้เป็นค่าเริ่มต้นของโปรเจ็คใหม่ · แอปที่แอดมิน
  เป็นคนสร้างผู้ใช้ให้จะไม่มีหน้าสมัคร ทำให้ไม่มีใครนึกถึงมัน แต่ endpoint ยังเปิดอยู่
  และ publishable key ถูกส่งไปกับ JavaScript ในเบราว์เซอร์ของทุกคนตามการออกแบบ
- **หลักฐาน:** `GET /auth/v1/settings` คืน `disable_signup: false` และ `external.email: true`
  บนโปรเจ็คที่เพิ่งสร้างและยังไม่มีตารางสักตัว · หลังปิดแล้วยิงซ้ำได้
  `disable_signup: true` · `anonymous_users: false` (30 ส.ค. 2569)
- **กฎกันซ้ำ:** โปรเจ็คที่ไม่มีหน้าสมัครสมาชิก ต้องปิด signup **ในเช็คลิสต์ตั้งค่าโปรเจ็ค**
  ไม่ใช่รอให้ audit เจอ · และการมี RLS ไม่ได้แปลว่าปลอดภัย — บัญชีขยะยังกิน MAU
  ส่งอีเมลจากโดเมนเรา และรอ policy ที่เขียนว่า `authenticated` เฉย ๆ สักอันเพื่อกลายเป็นรู
- **เจ้าของกฎ:** `nextjs-supabase-ssr-auth`

## กฎเดียว เขียนผิดสองร่าง พังคนละทิศ — และร่างที่สองอันตรายกว่า

กฎที่ต้องการ: *"ทุกไฟล์ที่ query Supabase ต้อง destructure `error` ออกมาเช็ค"*

- **ร่างที่ 1 — แดงตอนโค้ดถูก (false positive)**
  จับแค่ `.from(` แล้วไปโดน `Array.from({ length: rows })` ใน `states.tsx`
  ซึ่งไม่เกี่ยวกับ Supabase เลย · อาการนี้**ไม่อันตราย**เพราะมีคนมาดูภายในชั่วโมง
  แต่ถ้าปล่อยไว้ คนจะเรียนรู้ที่จะเมินตัวตรวจนี้ แล้วมันจะไร้ค่าตั้งแต่นั้น
- **🔴 ร่างที่ 2 — เขียวตลอดกาลโดยไม่ตรวจอะไรเลย (false pass)**
  แก้เป็น "ไฟล์ที่ import Supabase และมี `.from(`" แล้วเช็คว่ามีคำว่า `error` ไหม
  · แต่ `/\berror\b/` ไป**แมตช์ `console.error`** ที่มีอยู่แล้วในไฟล์เดียวกัน
  ผมลบ `const { data, error }` ออกจาก `branding.ts` จริง ๆ แล้ว **ตัวตรวจยังเขียว**
- **ร่างที่ 3 — ที่ใช้จริง** จับ `error` เฉพาะในตำแหน่ง destructure:
  `/const\s*\{[^}]*\berror\b[^}]*\}\s*=/` · red-test แล้วแดงจริง คืนไฟล์แล้วเขียวจริง
- **กฎกันซ้ำ:** **ตัวตรวจใหม่ทุกตัวต้อง red-test ด้วยการจงใจทำลายสิ่งที่มันเฝ้า**
  ถ้าไม่แดง แปลว่ายังไม่ใช่ตัวตรวจ · และ **คำที่ใช้เป็นสัญญาณต้องไม่ใช่คำที่โผล่ได้เอง
  ในบริบทอื่น** — `error` โผล่ใน `console.error`, `try/catch`, ชื่อตัวแปร, และคอมเมนต์
  ต้องผูกกับ**โครงสร้างไวยากรณ์** ไม่ใช่คำเปล่า ๆ
- **เจ้าของกฎ:** `kp-acceptance-test-matrix` (มีหัวข้อนี้อยู่แล้ว — เคสนี้เป็นตัวอย่างที่ครบทั้งสองขั้ว)

## อัปโหลดสำเร็จแต่บันทึกคีย์ไม่สำเร็จ = ไฟล์ค้างใน bucket ถาวร ไม่มีใครรู้

- **สาเหตุจริง:** การอัปโหลดเป็นสองขั้นที่แยกจากกัน — PUT เข้า R2 แล้วค่อย PATCH
  บันทึกคีย์ลงฐานข้อมูล · ขั้นแรกสำเร็จแต่ขั้นสองพัง (เน็ตหลุด ปิดแท็บ สิทธิ์ไม่พอ
  หรือในกรณีของผมคือยิงผิด HTTP method ได้ 405) → ไฟล์อยู่ใน bucket
  โดยไม่มีแถวไหนในฐานข้อมูลชี้ถึง **และไม่มีอะไรรายงานว่าเกิดขึ้น**
- **หลักฐาน:** ตอนสคริปต์ทดสอบยิง `POST` ไป endpoint ที่รองรับแค่ `PATCH`
  ไฟล์ใน `branding/` สะสมจาก 1 → 2 → 3 ทั้งที่แอปควรเก็บไว้แค่ไฟล์เดียว
  · ทุกคำขอ "สำเร็จ" ในสายตาผู้ใช้ ไม่มี error โผล่ที่ไหนเลย
- **กฎกันซ้ำ:** ทุกที่ที่อัปโหลดแยกเป็นสองขั้น ต้องมี **ตารางบันทึกความตั้งใจ**
  (`upload_intents`) เขียนตอนขอลิงก์ และมี **งานตามเวลาเก็บกวาด** ไฟล์ที่ไม่มีใคร
  อ้างถึงเกิน N ชั่วโมง · แค่ "ลบไฟล์เก่าตอนเปลี่ยน" ไม่พอ เพราะมันครอบเฉพาะทางที่สำเร็จ
  · ทางที่ล้มเหลวคือทางที่สร้างขยะ และเป็นทางที่ไม่มีใครทดสอบ
- **สถานะในโปรเจ็คนี้:** วางแผนไว้แล้วใน P2 (`upload_intents` + `sweep-orphans`)
  รอบนี้จึงยังไม่ทำ แต่บันทึกไว้เพราะมันไม่ใช่เรื่องเฉพาะสลิป — โลโก้ก็โดนเหมือนกัน
- **เจ้าของกฎ:** `supabase-rls-schema` (มีหัวข้อ "ห้าม insert → upload → update back" อยู่แล้ว
  แต่ยังไม่ครอบกรณี "upload แล้วไม่ได้ insert เลย")

## `tsc` แดงในไฟล์ที่เราไม่ได้เขียน — `.next/dev/types/validator.ts`

- **สาเหตุจริง:** รัน `next typegen` (ผ่าน `npm run typecheck`) ขณะที่ `next dev`
  กำลังเขียนไฟล์ชุดเดียวกันอยู่ · สองกระบวนการเขียนทับกันจนได้ไฟล์ที่ขาดกลาง
- **หลักฐาน:** `error TS1128: Declaration or statement expected` ที่บรรทัด 209
  ของไฟล์ที่ Next generate เอง · เปิดดูเจอชิ้นส่วนหัวขาด `xpected<typeof handler>`
  ซึ่งเป็นเศษของ `type __Check = __IsExpected<...>` · `rm -rf .next/dev/types`
  แล้วรันใหม่ → หายทันที และ error จริงในโค้ดเราค่อยโผล่ขึ้นมาแทน
- **กฎกันซ้ำ:** error ใน**ไฟล์ที่เครื่องมือสร้างเอง** ให้สงสัยว่าไฟล์เสียก่อนเสมอ —
  ลบแล้วสร้างใหม่หนึ่งครั้ง ก่อนจะไปไล่หาว่าโค้ดเราผิดตรงไหน
  · และถ้าจะให้เนียนกว่านั้น อย่ารัน typegen ขณะ dev server ทำงาน หรือแยก
  `--outDir` ของสองฝั่งออกจากกัน
- **เจ้าของกฎ:** `nextjs-gotchas`

## หน้า 500 ที่ต้นตออยู่ใน chunk เก่าที่เบราว์เซอร์แคชไว้ — และ source map คือตัวชี้เบาะแส

- **สาเหตุจริง:** Next dev เสิร์ฟ JavaScript chunk ด้วย **URL คงที่ ไม่มี content hash**
  เบราว์เซอร์จึงใช้ของเก่าซ้ำ · เซิร์ฟเวอร์เรนเดอร์ HTML จากโค้ดใหม่ แต่ client hydrate
  ด้วยโค้ดเก่าที่ยังรับ prop คนละชุด → พังตอน hydrate เท่านั้น
  · ลบ `.next` ไม่ช่วย เพราะของค้างอยู่ฝั่งเบราว์เซอร์ ไม่ใช่ฝั่งเซิร์ฟเวอร์
- **หลักฐาน:** `Cannot read properties of undefined (reading 'map')`
  ชี้ที่ `sidebar.tsx:39:72` ซึ่ง**คอลัมน์ 72 ตกอยู่กลางข้อความไทย** — เป็นตำแหน่งที่
  เป็นไปไม่ได้ · `groups.map` ตัวจริงอยู่บรรทัด 43 หลังจากเพิ่มคอมเมนต์ 3 บรรทัด
  แปลว่า **source map มาจาก build ก่อนหน้า** · ยิง HTML จาก node ได้ sidebar ครบทั้งสอง role
  (owner มี "รออนุมัติ" · supervisor ไม่มี) แต่แท็บเดิมยัง 500 · เปิดใน
  isolated context ที่ไม่มีแคช → ทำงานถูกทันที 6 เมนู ตรงตามที่ออกแบบ
- **กฎกันซ้ำ:** **ตำแหน่งใน stack ที่เป็นไปไม่ได้ในไฟล์ปัจจุบัน = โค้ดที่รันอยู่ไม่ใช่โค้ดที่เห็น**
  หยุดอ่านโค้ดแล้วไปตรวจว่าอะไรถูกเสิร์ฟจริง · วิธีตัดจบคือ **เปิดใน browser context ใหม่ที่ไม่มีแคช**
  ไม่ใช่ reload ธรรมดาและไม่ใช่ลบ `.next` · และก่อนสรุปว่าโค้ดผิด ให้เทียบ
  **HTML ที่เซิร์ฟเวอร์ส่งออกมา** ก่อนเสมอ — ถ้า SSR ถูก ปัญหาอยู่ที่ client ล้วน ๆ
  ซึ่งตัดพื้นที่ค้นหาทิ้งไปครึ่งหนึ่งทันที
- **เจ้าของกฎ:** `kp-testing-cadence` · `nextjs-gotchas`

## รายงานว่า "tsc เขียว" ทั้งที่ tsc แดง

- **สาเหตุจริง:** ต่อ `| tail -20` ท้ายคำสั่ง · ใน bash exit code ของ pipeline คือของ
  **คำสั่งสุดท้าย** ซึ่งคือ `tail` และ `tail` สำเร็จเสมอ · `cmd && echo "เขียว"` จึงพิมพ์ "เขียว" ทุกครั้ง
  ต่อให้ `cmd` จะพังยับ
- **หลักฐาน:** `npx tsc --noEmit 2>&1 | tail -20 && echo "tsc เขียว"` พิมพ์ทั้ง

  — นี่คือรูปธรรมของ "exit code 0 ไม่ใช่หลักฐาน" ที่เขียนไว้ใน runbook แล้วยังพลาดเอง

## สคริปต์ตรวจคอนทราสต์ขึ้นเขียว แต่ไม่เคยตรวจโหมดมืดเลยสักครั้ง

- **สาเหตุจริง:** `verify-contrast.mjs` หาบล็อกด้วย `css.indexOf('.dark')` · แต่ไฟล์ tokens.css
  มีบรรทัด `@custom-variant dark (&:where(.dark, .dark *));` อยู่ **ก่อน** `:root`
  `indexOf` เลยไปเจอคำว่า `.dark` ในบรรทัดนั้น แล้ว slice ไปจบที่ `\n}` ตัวแรก ซึ่งคือท้ายบล็อก `:root`
  ผลคือ `dark = {...light, ...light}` — **โหมดมืดถูกวัดด้วยค่าของโหมดสว่างทุกครั้ง**
- **หลักฐาน:** รายงานพิมพ์ตัวเลข LIGHT กับ DARK **เท่ากันเป๊ะทั้ง 29 บรรทัด** ซึ่งเป็นไปไม่ได้
  ถ้าสองบล็อกมีค่าต่างกันจริง · พอแก้แล้ว DARK เปลี่ยนเป็นชุดตัวเลขของตัวเอง
  (เช่น `status-done on surface` 6.60 → 9.03) และเจอ `WHITE on urgent-solid` = 4.99 ที่ไม่เคยถูกวัดมาก่อน
- **กฎกันซ้ำ:** หา CSS selector ต้องใช้ regex ที่ยึด**ต้นบรรทัดและปีกกาที่ตามมา**
  (`/^[ \t]*\.dark\s*\{/m`) ไม่ใช่ `indexOf` ชื่อเปล่า ๆ — ชื่อ selector โผล่ในที่อื่นของไฟล์ได้เสมอ
  · และกฎที่ใหญ่กว่านั้น: **ผลตรวจที่ออกมาเหมือนกันสองชุดเป๊ะ ๆ คืออาการของตัวตรวจพัง ไม่ใช่หลักฐานว่าผ่าน**
  ตัวตรวจที่แดงไม่เป็น แย่กว่าไม่มีตัวตรวจ เพราะมันสร้างความมั่นใจปลอม
- **เจ้าของกฎ:** `thai-admin-page-kit` (สคริปต์ที่คิตส่งมาเอง — ทุกโปรเจ็คที่ใช้คิตนี้
  ส่งโหมดมืดที่ไม่เคยถูกตรวจ) · หลักการเรื่อง "ตัวตรวจต้องแดงเป็น" เป็นของ `kp-acceptance-test-matrix`

## heredoc ของ Bash กลืน backslash คู่ ทำให้ regex เปลี่ยนความหมายเงียบ ๆ

- **อาการที่คนจะรายงาน:** "โค้ดที่เพิ่งเขียนไป syntax error ทั้งที่ตอนพิมพ์ถูกแน่ ๆ"
- **สาเหตุจริง:** เขียนไฟล์ด้วย `cat > f <<'EOF'` แล้ว backslash **สองตัว** ในเนื้อหา
  ถูกยุบเหลือตัวเดียว (แต่ `$` กับ `${}` ไม่ถูกแทนค่า — จึงดูเหมือน heredoc ทำงานถูกต้อง)
  คลาสอักขระที่ตั้งใจจะจับ backslash จึงกลายเป็นการ escape วงเล็บเหลี่ยมปิดแทน
  → regex ไม่ปิด · เอกสารบทเรียนอันนี้เองก็โดนกลืนรอบแรกด้วยเหตุผลเดียวกัน
- **หลักฐาน:** `tsc` แดงที่ `sites/page.tsx(19,44) TS1161: Unterminated regular expression`
  · รอบถัดมา anchor ของ Python (`"\n══"`) กลายเป็นขึ้นบรรทัดใหม่จริง
  `str.replace` จึงไม่แมตช์ แล้ว `print("ok")` ยังพิมพ์ว่าสำเร็จ — **เขียวโดยไม่ได้แก้อะไร**
- **กฎกันซ้ำ:** ไฟล์ที่มี backslash (regex, path, escape sequence) เขียนด้วยเครื่องมือ
  Write/Edit ไม่ใช่ heredoc · และ `str.replace` ที่ไม่แมตช์ต้อง **โยน error**
  ไม่ใช่คืนสตริงเดิมเงียบ ๆ — เช็คก่อนเขียนกลับเสมอว่าเนื้อหาเปลี่ยนจริง
- **เจ้าของกฎ:** `kp-autonomous-loop` (เครื่องมือแก้ไฟล์ระหว่างรันยาว)

## negative lookahead หลัง `\s*` ผ่านตลอด เพราะ `\s*` ถอยไปแมตช์ศูนย์ตัวได้

- **อาการที่คนจะรายงาน:** "ตัวตรวจบอกว่าทุกคอลัมน์มีคนเขียนแล้ว" — แล้วก็มีคอลัมน์ที่ว่างตลอดกาล
- **สาเหตุจริง:** เขียนกฎว่า "คอลัมน์ต้องตามด้วยโคลอนแล้วค่าที่ไม่ใช่ชื่อชนิดข้อมูล"
  เป็น `col\s*:\s*(?!string|number)` · เอนจิน regex ถอยกลับ (backtrack) ให้ `\s*`
  ตัวหลังแมตช์ **ศูนย์ตัวอักษร** ได้ ตำแหน่งที่ lookahead ไปตรวจจึงเป็น *ตัวเว้นวรรค*
  ไม่ใช่คำว่า `string` → เงื่อนไข "ต้องไม่ใช่ string" เป็นจริงเสมอ
  ผลคือ `client_name: string | null` ในนิยาม type ถูกนับว่า "มีคนเขียนค่า"
- **หลักฐาน:** ลบ `planned_date: date.value` ออกจาก payload ของ route จนทั้งไฟล์ไม่เหลือคำนี้
  (`grep -c` = 0) แล้วแถว P1-DB-12 **ยังเขียว** · แก้เป็นการ **จับค่า** หลังโคลอน
  ออกมาเทียบกับเซ็ตของชื่อชนิดข้อมูลตรง ๆ แล้ว red-test ซ้ำ → แดงถูกต้อง
- **กฎกันซ้ำ:** อย่าวาง negative lookahead ไว้หลัง quantifier ที่แมตช์ศูนย์ตัวได้
  ให้ **จับกลุ่มแล้วเทียบใน JS** แทน · และกฎที่ใหญ่กว่า: ตัวตรวจแนว "grep หาว่ามีโค้ดทำ X ไหม"
  ต้อง red-test ด้วยการ **ลบโค้ดนั้นออกจริง ๆ** แล้วดูว่าแดง — ไม่ใช่แค่อ่านแล้วเชื่อว่ามันถูก
  · อีกกับดักในตระกูลเดียวกันที่เจอในรอบเดียวกัน: สตริงของ `.select('a, b, c')`
  ทำให้ทุกคอลัมน์ในลิสต์ดูเหมือนถูก *เขียน* ทั้งที่มันคือการ *อ่าน* → ต้องตัดสตริงทิ้งก่อน grep
- **เจ้าของกฎ:** `kp-acceptance-test-matrix`

## ฟังก์ชันรวมยอดที่เผลอเป็น `security definer` = ตัวเลขทั้งบริษัทหลุดโดยหน้าจอดูปกติ

- **อาการที่คนจะรายงาน:** ไม่มีอาการ · หน้าภาพรวมของหัวหน้าโครงการแสดงตัวเลขสวยงาม
  มีการ์ดครบ ไม่มี error ไม่มีอะไรผิดสังเกต — แค่เป็นตัวเลขของทั้งบริษัท
- **สาเหตุจริง:** ตัวเลขบนแดชบอร์ดต้องนับในฐานข้อมูล (ห้ามดึงแถวมานับใน JS
  เพราะ PostgREST ตัดที่ 1,000 แถวเงียบ ๆ) จึงต้องเขียนเป็นฟังก์ชัน SQL ·
  และ `security definer` เป็นสิ่งที่นิ้วพิมพ์เองโดยอัตโนมัติ เพราะฟังก์ชัน SQL
  ส่วนใหญ่ในโปรเจ็ค (`is_owner()` `supervises_site()`) ต้องเป็น definer จริง ๆ
  · แต่ definer = **ปิด RLS ข้างใน** → `sum()` วิ่งทับทุกแถวในตาราง
- **หลักฐาน:** เปลี่ยน `site_overview()` เป็น definer แล้วหัวหน้าโครงการได้
  `active_contract = 3000000` (ทั้งบริษัท) แทน `1000000` (ของตัวเอง)
  · เปลี่ยนกลับเป็น invoker แล้วได้ 1000000 · ทั้งสองรอบหน้าจอเรนเดอร์ปกติ
- **กฎกันซ้ำ:** ฟังก์ชันที่ **อ่านข้อมูลเพื่อเอาไปแสดง** ต้องเป็น `security invoker`
  ให้ RLS ทำงานต่อ · `security definer` ใช้เฉพาะฟังก์ชันที่ต้อง**ข้าม** RLS
  โดยเจตนา (helper ที่ policy เรียกเอง ซึ่งถ้าไม่ข้ามจะ recursion)
  · และตัวตรวจต้อง **เทียบสองบทบาทในการตรวจเดียวกัน** — ตรวจฝั่งเจ้าของอย่างเดียว
  ได้เลขถูกทั้งสองแบบ แยกไม่ออก
- **เจ้าของกฎ:** `supabase-rls-schema` (มีหัวข้อ definer อยู่แล้ว แต่พูดถึงเคส
  "ฟังก์ชันสาธารณะ" · เคสนี้คือ **ฟังก์ชันรวมยอดของแดชบอร์ด** ซึ่งเป็นที่ที่
  definer ดูสมเหตุสมผลที่สุดและอันตรายที่สุด)

## ตัวตรวจที่ดีเกินไปหนึ่งก้าว: จับ `const {` แต่ไม่จับ `const [{`

- **อาการที่คนจะรายงาน:** "ตัวตรวจแดงใส่โค้ดที่ถูกต้อง"
- **สาเหตุจริง:** กฎ "ต้อง destructure `error`" ถูกผูกกับ `const\s*\{…error…\}\s*=`
  พอเขียน `const [{ data, error: aErr }, { data, error: bErr }] = await Promise.all([…])`
  เพื่อยิงสอง query พร้อมกัน — เช็ค error ครบทั้งคู่ แต่ pattern เริ่มด้วย `[`
- **หลักฐาน:** `P0-SEC-05` แดงใส่ `src/app/(app)/page.tsx` ที่เช็ค error ครบทั้งสองตัว
- **กฎกันซ้ำ:** false positive อันตรายพอ ๆ กับ false pass — คนละกลไก แต่ปลายทางเดียวกัน
  คือคนเลิกเชื่อตัวตรวจ · แก้เป็นการดึง **ข้อความระหว่าง `const` กับ `=`** ออกมา
  แล้วค่อยหา `error` ในนั้น ซึ่งครอบทั้งรูป `{…}` และ `[{…}, {…}]`
  โดยยังไม่ไปแมตช์ `console.error` · **red-test ทั้งสองทิศทุกครั้ง**: ทำลายของจริงต้องแดง
  และโค้ดที่ถูกในทุกสำนวนที่ทีมใช้จริงต้องเขียว
- **เจ้าของกฎ:** `kp-acceptance-test-matrix`

## "ซ่อนตัวเลขบนหน้าจอ" ไม่ใช่การคุมสิทธิ์ — และ column grant ก็ช่วยไม่ได้

- **อาการที่คนจะรายงาน:** ไม่มีอาการ · เจ้าของบอกว่า "ค่างานเป็นความลับจากหัวหน้าโครงการ"
  แล้วคนทำก็เอา `{isOwner && <span>{amount}</span>}` ครอบไว้ ซึ่งดูเหมือนเสร็จแล้ว
- **สาเหตุจริง (สองชั้น):**
  1. หน้าจอไม่แสดงไม่ได้แปลว่าอ่านไม่ได้ — หัวหน้าโครงการเรียก PostgREST ตรงด้วย
     token ของตัวเองก็ได้ทั้งแถว เพราะ RLS อนุญาตให้เขาเห็น**แถว**ของโครงการที่ดูแล
  2. ทางแก้ที่นึกออกทันทีคือ `revoke select (contract_amount) from authenticated`
     — **ใช้ไม่ได้** เพราะสิทธิ์ระดับคอลัมน์ให้กับ **role ของฐานข้อมูล** แต่เจ้าของ
     กับหัวหน้าโครงการเข้ามาเป็น role เดียวกันคือ `authenticated` · ตัวตนที่ต่างกัน
     อยู่ใน JWT ไม่ได้อยู่ใน role · revoke แล้วเจ้าของก็อ่านไม่ได้ด้วย
- **หลักฐาน:** เปิด policy ของ `site_finance` ให้ `using (true)` ชั่วคราว → หัวหน้าโครงการ
  อ่านได้ 2 แถวทันทีทั้งที่หน้าจอไม่เคยแสดงตัวเลขให้เขาเลย · คืน policy แล้วได้ 0 แถว
- **กฎกันซ้ำ:** **RLS คุมได้ระดับแถว ค่าที่คนละบทบาทเห็นไม่เท่ากันจึงต้องอยู่คนละแถว
  = คนละตาราง** · แล้วปิดให้ครบทุกทาง ไม่ใช่ทางเดียว: ตารางเดิมต้องไม่เหลือคอลัมน์นั้น
  · ฟังก์ชันรวมยอดต้องคืน **`null` ไม่ใช่ `0`** (หน้าจอซ่อนการ์ดที่ได้ null ได้
  แต่จะวาด ฿0 อย่างมั่นใจแล้วคนอ่านจะเชื่อ) · และหน้าจอไม่แสดง — สามชั้น สามการทดสอบ
  โดยชั้นหน้าจอเป็นชั้นที่**อ่อนที่สุด** ไม่ใช่ชั้นที่นับ
- **เจ้าของกฎ:** `supabase-rls-schema` (สกิลบอกว่า "ซ่อนปุ่มไม่ใช่ access control" แล้ว
  แต่ยังไม่ได้อธิบายว่า **column grant แก้ไม่ได้** เมื่อทุกบทบาทใช้ role `authenticated`
  ร่วมกัน ซึ่งเป็นกรณีของ Supabase ทุกโปรเจ็ค)

## policy เขียนว่า `created_by = auth.uid()` แต่ไม่มีอะไรเติม `created_by` เลย

- **อาการที่คนจะรายงาน:** "กดบันทึกแล้วขึ้นว่าสำเร็จ แต่ข้อมูลไม่เปลี่ยน"
  · ฝั่ง API ได้ **200** ทุกครั้ง ไม่มี error ที่ไหนเลย
- **สาเหตุจริง:** คอลัมน์ `created_by` ไม่มี default และ PostgREST ไม่ได้ส่งมา
  ค่าจึงเป็น `null` · เงื่อนไข `null = auth.uid()` ให้ผลเป็น **`null` ไม่ใช่ `false`**
  ซึ่ง RLS ถือว่าไม่ผ่าน → แถวถูกตัดออกจาก `UPDATE` → โดน 0 แถว → ตอบ 200 สำเร็จ
- **ผลที่ตามมาสองอย่าง และอันที่สองแย่กว่า:**
  1. คนที่ควรแก้รายการของตัวเองได้ แก้ไม่ได้เลย
  2. **สาขา `created_by = auth.uid()` ของ *ทุก* policy ตายสนิทโดยไม่มีอะไรฟ้อง**
     กฎที่เขียนไว้ครบถ้วนสวยงาม อ่านแล้วเหมือนมีการป้องกันอยู่ แต่เป็นจริงไม่ได้เลยสักครั้ง
     — ญาติสนิทของ "กฎที่ถูกบังคับที่ระดับซึ่งมันไม่มีวันเป็นจริง"
- **หลักฐาน:** `select count(*), count(created_by) from transactions` → `0 / 0`
  · แถว P2-DB-04 คาดว่าจะได้ `APPROVE_FORBIDDEN` แต่ได้ **200 · สถานะยัง pending**
  ซึ่งเป็นลายเซ็นของ "RLS ตัดแถวออกก่อน trigger จะได้พูด"
- **กฎกันซ้ำ:** คอลัมน์ที่ policy ใช้ตัดสินสิทธิ์ **ต้องถูกเติมโดยฐานข้อมูล**
  และเติมใน **trigger ไม่ใช่ `default auth.uid()`** เพราะ default ถูก client ส่งค่าทับได้
  (เท่ากับสร้างรายการในนามคนอื่น — เรื่องเดียวกับ "ห้ามเชื่อ role ที่ client ส่งมา")
  · และวางกฎให้ **`using` คุมว่าแตะแถวไหนได้ ส่วน `with check` อย่าใส่เงื่อนไขที่
  ตั้งใจจะปฏิเสธพร้อมเหตุผล** — ให้ trigger เป็นคนปฏิเสธ ผู้ใช้จะได้เห็นว่าทำไม
  แทนที่จะได้ 200 เปล่า ๆ
- **วิธีตรวจที่จับได้:** ทุก policy ที่อ้างคอลัมน์ ให้มีแถวที่พิสูจน์ **ฝั่งบวก** ด้วย —
  "คนที่ควรทำได้ ทำได้จริง" · แถวที่ทดสอบแต่การปฏิเสธจะเขียวตลอดกาลเมื่อกฎตายไปแล้ว
- **เจ้าของกฎ:** `supabase-rls-schema`

## ตัวกวาดไฟล์กำพร้าที่ลบเกิน — และการทดสอบที่ไม่มีวันจับได้

- **อาการที่คนจะรายงาน:** "กดดูสลิปของเดือนที่แล้วแล้วรูปไม่ขึ้น" · เกิดหลังจาก
  ข้อมูลถูกลบไปแล้วเป็นสัปดาห์ ไม่มีใครเชื่อมโยงกับงานกวาดที่รันทุกชั่วโมง
- **สาเหตุจริง:** ตัวกวาดเลือกแถวจาก `expires_at < now()` แต่ลืมเงื่อนไข
  `consumed_at is null` · ไฟล์ที่ถูกแนบกับรายการจริงแล้วก็หมดอายุ **ความตั้งใจ**
  เหมือนกัน — สิ่งที่หมดอายุคือใบอนุญาตอัปโหลด ไม่ใช่ตัวไฟล์
- **หลักฐาน:** ลบเงื่อนไขออกแล้วรันตัวตรวจ — ลบไป **4 ไฟล์แทนที่จะเป็น 2**
  โดยสองไฟล์ที่เกินคือสลิปของรายการที่บันทึกสำเร็จแล้ว
- **🔴 กับดักที่อันตรายกว่า: ตัวตรวจรุ่นแรกจับไม่ได้เลย** เพราะมันปล่อยให้
  ไฟล์ที่ใช้แล้วมี `expires_at` อยู่ในอนาคต · ไฟล์นั้นจึงรอด **เพราะยังไม่หมดอายุ**
  ไม่ใช่เพราะตัวกวาดเคารพ `consumed_at` — แถวนั้นเขียวเท่ากันทั้งตอนโค้ดถูกและผิด
- **กฎกันซ้ำ:** แถวที่ยืนยันว่า "X ต้องไม่ถูกแตะ" ต้องจัดฉากให้ **X เข้าเงื่อนไข
  การถูกแตะทุกข้อยกเว้นข้อที่กำลังทดสอบ** · ไม่งั้นมันรอดด้วยเหตุผลอื่น
  และแถวนั้นก็ไม่เคยทดสอบอะไรเลย · เป็นญาติของ `0 === 0` แต่จับยากกว่า
  เพราะผลลัพธ์ "ไฟล์ยังอยู่" ดูเหมือนคำตอบที่ถูกต้องทุกประการ
- **เจ้าของกฎ:** `kp-acceptance-test-matrix`

- **อาการที่คนจะรายงาน:** "ค้นชื่อร้านที่มีคอมมาแล้วไม่เจอ ทั้งที่ตาเห็นอยู่ในลิสต์"

## ชนิดที่ Supabase สร้างให้บอกว่าคอลัมน์ของ RPC ไม่มีวันเป็น null — ทั้งที่มันเป็น

- **อาการที่คนจะรายงาน:** "หน้าจอขึ้น ฿NaN" หรือ "ตัวเลขเป็น 0 ทั้งที่ควรจะหายไป"
- **สาเหตุจริง:** `generate_typescript_types` เขียนทุกคอลัมน์ของ `returns table`
  เป็น non-null เสมอ เพราะ Postgres ไม่ได้ประกาศ nullability ของ OUT parameter
  ไว้ที่ไหนให้อ่าน · ฟังก์ชันที่จงใจคืน `null` แปลว่า "ไม่มีสิทธิ์เห็นตัวเลขนี้"
  (ตามกฎ "คืน null ไม่ใช่ 0") จึงถูกชนิดปลอมกลบไป — `tsc` ไม่ยอมให้เขียน
  `x !== null` ในบางบริบท และคนเขียนโค้ดก็เชื่อชนิดแล้วข้ามการเช็คไปเลย
- **หลักฐาน:** `site_money()` คืน `contract_amount: numeric` ที่เป็น `null`
  สำหรับหัวหน้าโครงการ แต่ `database.types.ts` เขียนว่า `contract_amount: number`
  · เอาไปหารตรง ๆ ได้ `NaN` ที่เรนเดอร์ออกมาเป็นข้อความจริงบนหน้าจอโดยไม่มี error
- **กฎกันซ้ำ:** RPC ที่คืน `null` แทน "ไม่มีสิทธิ์เห็น" ต้องมีตัวแปลงหนึ่งชั้น
  (`asNullableNumber()`) และโค้ดหน้าจอห้ามอ่านฟิลด์ดิบจากผลของ RPC เลย ·
  ให้ชนิดของแอปเป็นความจริง ไม่ใช่ชนิดที่เครื่องมือเดาให้ · และต้องมีแถวตรวจรับ
  ที่**ล็อกอินด้วย role ที่ไม่มีสิทธิ์** แล้วยืนยันว่าไม่มีคำว่า `NaN` บนหน้า
- **เจ้าของกฎ:** `supabase-rls-schema`

## `realtime.send()` กลืน error ทุกชนิด — broadcast หายทั้งระบบโดยไม่มีใครรู้

- **อาการที่คนจะรายงาน:** "แจ้งเตือนไม่เด้ง" ทั้งที่ข้อมูลในตารางถูกต้องครบทุกแถว
- **สาเหตุจริง:** ตัวฟังก์ชัน `realtime.send()` ห่อ `INSERT INTO realtime.messages`
  ไว้ใน `BEGIN … EXCEPTION WHEN OTHERS THEN RAISE WARNING` — **ทุก** ความล้มเหลว
  จึงกลายเป็น warning ที่ไม่มีใครเห็น · บนโปรเจ็คที่ยังไม่เคยใช้ Realtime เลย
  `realtime.messages` ยังไม่มี partition สักวัน insert จึงล้มทุกครั้ง
  แล้ว trigger ก็ commit ต่อไปตามปกติ
- **หลักฐาน:** `select prosrc from pg_proc` เห็น exception handler ชัด ๆ ·
  ยิง insert ตรง ๆ ได้ `23514: no partition of relation "messages" found for row` ·
  ต่อ websocket ครั้งแรกได้ `CHANNEL_ERROR MissingPartition` แล้ว Realtime
  สร้าง partition ให้ 5 วันล่วงหน้า หลังจากนั้นทุกอย่างทำงานทันที
- **กฎกันซ้ำ:** สองข้อ
  1. ต้องมีแถวตรวจรับที่ยืนยันว่า **ข้อความลงถึง `realtime.messages` จริง**
     ไม่ใช่แค่ "trigger ถูกสร้างแล้ว" — เพราะ trigger ที่ทำงานสำเร็จกับ
     trigger ที่ส่งข้อความไม่ออกหน้าตาเหมือนกันเป๊ะ
  2. ฝั่ง client ต้อง **subscribe แบบมี retry** ไม่ยอมแพ้ที่ `CHANNEL_ERROR`
     ครั้งแรก — ครั้งแรกของโปรเจ็คใหม่ (และของทุกวันที่ partition ขาด) จะพลาดเสมอ
     แล้วครั้งถัดไปจะสำเร็จ
- **เจ้าของกฎ:** `supabase-rls-schema`

## snapshot ที่ถูกถ่ายใหม่ทุกครั้งที่แถวถูกแตะ ไม่ใช่ snapshot

  แถวตรวจ ไม่ใช่คอมเมนต์ที่เขียนไว้ข้างบนมัน

## สคริปต์ seed ผ่านมาตลอด แล้วพังครั้งแรกตอนรันบนฐานข้อมูลที่ล้างใหม่

- **อาการ:** `invalid input syntax for type uuid: "undefined"` — สคริปต์ seed
  ที่รันผ่านมาหลายสิบครั้ง พังทันทีที่รันบนฐานข้อมูลที่เพิ่งล้าง ซึ่งคือ
  สภาพเดียวกับเครื่องของลูกค้าตอนติดตั้งครั้งแรก
- **สาเหตุ:** คำสั่งเดียวที่ยัด `insert` ไว้ใน CTE แล้วอ่านผลกลับจากตารางเดิม
  ตอนท้าย — ทุกส่วนของคำสั่งเดียวกันเห็น snapshot เดียวกัน (ตอนคำสั่งเริ่ม)
  แถวที่ CTE เพิ่งเขียนจึงไม่อยู่ในนั้น · `select` ท้ายคำสั่งคืนศูนย์แถว
  แผนที่ id ว่างเปล่า แล้ว `undefined` ไหลลงไปเป็นสตริงใน SQL ก้อนถัดไป
- **หลักฐาน:** ฐานที่มีข้อมูลอยู่ก่อน → `โครงการ 5 · รายการ 20` ผ่าน ·
  ฐานที่ล้างใหม่ → `โครงการ 0→5 · รายการ 0→0` แล้ว throw
- **กฎกันซ้ำ:** ในคำสั่งเดียว **เขียนแล้วอ่านกลับไม่ได้** — แยกเป็นสองคำสั่ง
  (เขียนให้จบ แล้วค่อยอ่าน) หรือ `union all` ผล `returning` เข้ากับของเดิม ·
  และสำคัญกว่านั้น: **สคริปต์ seed ต้องถูกตรวจบนฐานข้อมูลที่ว่างจริง ๆ**
  ไม่ใช่บนฐานที่มันเคย seed ไว้แล้ว มิฉะนั้นการตรวจจะยืนยันแค่ว่า
  "ข้อมูลที่มีอยู่แล้วยังอยู่"
- **เจ้าของกฎ:** `kp-seed-and-reset`

## แถวตรวจ "idempotent" ที่ไม่เคยรัน seed รอบที่สอง

- **อาการ:** แถว `P8-SEED-02 รันซ้ำแล้วจำนวนแถวเท่าเดิม` เขียวมาตลอด
  แล้วแดงทันทีที่ฐานข้อมูลว่าง โดยที่ตัว seed เองไม่ได้ผิด
- **สาเหตุ:** โค้ดนับก่อน-seed เทียบหลัง-seed ของการรัน **ครั้งเดียว** ·
  สองค่านั้นเท่ากันได้ก็ต่อเมื่อฐานมีข้อมูลครบอยู่ก่อนแล้ว ซึ่งแปลว่า
  ตอนเขียวมันวัด "ข้อมูลเดิมไม่ถูกแตะ" ไม่ใช่ "รันซ้ำแล้วไม่เพิ่ม" —
  seed รอบที่สองไม่เคยถูกเรียกเลยสักครั้ง
- **หลักฐาน:** `โครงการ 0→5 · รายการ 0→20` ถูกรายงานว่า "ไม่ idempotent"
  ทั้งที่ตัวเลขนั้นคือการ seed รอบแรกที่ทำงานถูกต้อง
- **กฎกันซ้ำ:** แถวที่พูดว่า "ทำซ้ำแล้วผลเท่าเดิม" ต้อง **ลงมือทำซ้ำจริง**
  ในตัวแถวเอง แล้วเทียบรอบที่ N กับรอบที่ N+1 · เทียบกับสถานะก่อนเริ่ม
  เป็นคนละคำถาม และเป็นคำถามที่ตอบว่า "ผ่าน" ได้โดยไม่ต้องทดสอบอะไรเลย
- **เจ้าของกฎ:** `kp-acceptance-test-matrix`

## `loading.tsx` ทำให้ `notFound()` และ `redirect()` เงียบหายไปทั้งเฟส

- **อาการ:** ใส่ `loading.tsx` เพื่อให้มีสถานะโครงร่างครบตามข้อกำหนด แล้ว
  `/sites/<uuid ที่ไม่มีอยู่>` เปลี่ยนจาก **404 เป็น 200** และหน้าที่เฉพาะ
  เจ้าของเข้าได้ 4 หน้าเปลี่ยนจาก **เด้งจริงเป็น 200** พร้อมกันทั้งชุด
- **สาเหตุ:** `loading.tsx` ห่อ segment ด้วย Suspense → คำตอบกลายเป็นสตรีม
  ที่ **ส่งหัว 200 ออกไปแล้ว** ก่อน page จะได้ทำงาน · `notFound()` กับ
  `redirect()` ที่อยู่ใน page จึงตั้งรหัสสถานะไม่ได้อีก กลายเป็นการเด้ง
  ฝั่ง client แทน — เบราว์เซอร์ยังไปถูกที่ แต่ทุกอย่างที่ไม่ใช่เบราว์เซอร์
  เห็น 200 · ไม่มี error ไม่มี warning
- **หลักฐาน:** ถอด `loading.tsx` ที่อยู่เหนือ `[id]` ออกทั้งสองชั้น → 404 กลับมา
  ทันที · และแถว `P3-UI-02` `P4-UI-02` `P5-UI-02` `P6-UI-02` แดงพร้อมกัน
  ด้วยข้อความเดียวกันเป๊ะ: `200 → (ไม่มี location)`
- **กฎกันซ้ำ:** ได้ทั้งสองอย่างโดยย้ายที่วางแทนการเลือกข้าง —
  · การเช็ค role ย้ายไป **`layout.tsx`** ซึ่งเรนเดอร์ *นอก* Suspense ของ page
  · หน้าที่มี `notFound()` ห้ามมี `loading.tsx` อยู่เหนือมันเลยแม้แต่ชั้นเดียว —
    ใช้ **route group** `(list)` / `(overview)` ให้ขอบเขตของ Suspense ไม่คลุม
    segment ที่เป็น dynamic
  · และต้องมีแถวตรวจที่ยิงจริงว่า "ของที่ไม่มีอยู่ตอบ 404" กับ "role ที่ไม่มี
    สิทธิ์โดนเด้ง" ไม่งั้นการถอยกลับแบบนี้จะไม่มีใครเห็นจนถึงวันส่งมอบ
- **เจ้าของกฎ:** `nextjs-gotchas`

## `401` + `WWW-Authenticate` ไม่ใช่ "บอกว่าคีย์ผิด" แต่คือ "เริ่ม OAuth ได้เลย"

- **อาการ:** connector ที่เพิ่มใน claude.ai ค้างอยู่หลังปุ่ม **Connect** ที่กดยังไงก็
  ไม่ผ่าน · ไม่มีข้อความ error ที่ไหนเลย ทั้งบนหน้าจอ ทั้งใน log ของเรา
  (เพราะฝั่งเราตอบ 401 ตามที่ตั้งใจไว้ทุกประการ)
- **สาเหตุ:** ตามสเปก MCP header `WWW-Authenticate` บนคำตอบ 401/403 คือ**สัญญาณ
  ให้ client ไปทำ OAuth discovery** · client จะยิงหา
  `/.well-known/oauth-protected-resource` เจอ 404 แล้วรอต่อไปเรื่อย ๆ
  · นี่คือ header ที่**วิศวกรที่รอบคอบจะตั้งใจใส่** เพราะมันดูถูกต้องตาม RFC 7235
  แล้วมันจะทำให้ของที่กำลังสร้างพังโดยที่ทุกอย่างดู "ทำตามสเปก" หมด
- **กฎกันซ้ำ:** เซิร์ฟเวอร์ MCP ที่ยืนยันตัวตนด้วยคีย์ใน URL **ห้ามส่ง
  `WWW-Authenticate` ในคำตอบใด ๆ** ทั้ง 401 และ 403 · เขียนเป็นแถวตรวจที่อ่าน
  header ตรง ๆ (`P9-PROTO-01`) ไม่ใช่คอมเมนต์เตือน — คอมเมนต์ไม่กันคนถัดไปที่
  "แก้ให้ถูกตามสเปก"
- **เจ้าของกฎ:** `mcp-analytics-connector`

## `service_role` ไม่มีตัวตน — RPC ที่ห่อด้วย `is_owner()` คืน null ทั้งแผงอย่างเงียบ ๆ

- **อาการ:** เรียก RPC เงินเดิมของแอป (`site_money` / `site_overview`) ด้วย secret key
  จากฝั่งเซิร์ฟเวอร์ ได้ **200 พร้อมแถวครบ** แต่ทุกคอลัมน์เงินเป็น `null`
  · ไม่มี error ที่ไหน และ AI ที่ได้ข้อมูลชุดนี้ไปจะไม่ทักเลย มันจะตอบคำถาม
  เรื่องกำไรด้วยความมั่นใจจากตัวเลขที่ไม่มีอยู่
- **สาเหตุ:** RPC พวกนั้นเป็น `security invoker` และห่อคอลัมน์เงินด้วย
  `case when public.is_owner() then …` ซึ่งอ่าน `auth.uid()` · secret key ไม่มี claim
  `sub` → `auth.uid()` เป็น null → `is_owner()` เป็นเท็จ → คอลัมน์เป็น null ไม่ใช่ error
- **กฎกันซ้ำ:** อย่าคัดลอกสูตรเงินไปไว้อีกที่หนึ่งเพื่อให้ service key อ่านได้ ·
  ทำ helper `security definer` ที่ **สวมสิทธิ์เจ้าของภายในทรานแซกชัน**
  (`set_config('request.jwt.claims', …, is_local := true)` หลังตรวจว่า actor เป็น
  `owner` และ `is_active` จริง) แล้วเรียกของเดิม — สูตรอยู่ที่เดียวตลอดไป
  · และ **ห้ามใส่ทางลัด `auth.uid() is null` ให้ service ผ่าน** ใน helper ที่ `anon`
  เรียกได้ (CLAUDE.md §5)
- **แถวที่กันไว้:** `P9-FN-03` / `P9-FN-04` ต้อง**นับ null แยกต่างหาก** ไม่ใช่แค่เทียบ
  เท่ากัน — `null is distinct from null` เป็นเท็จ แถวจึงเขียวได้ทั้งที่ทั้งสองฝั่งว่าง
  ซึ่งเป็นหน้าตาของบั๊กนี้พอดี
- **เจ้าของกฎ:** `supabase-rls-schema`

## เปิดสิทธิ์ให้ role ใหม่เขียนตารางเดิม — ทุกสูตรที่เคยอ่านตารางนั้นเปลี่ยนความหมายพร้อมกัน

- **อาการ:** เจ้าของสั่งให้หัวหน้าโครงการ "ตั้งเบิกค่าแรงให้ลูกน้อง แล้วผมอนุมัติทีหลัง"
  · เพิ่มคอลัมน์ `status` ลง `advances` เสร็จ ทุกอย่างดูจบ — แต่แถวชนิดใหม่ที่เกิดขึ้น
  (`pending` = **คำขอ ยังไม่ใช่เงิน**) ถูกสูตรเก่าทั้งห้าตัวนับเป็นเงินที่จ่ายไปแล้วทันที
- **สาเหตุ:** สูตรพวกนั้นเขียนตอนที่ **ทุกแถวในตารางแปลว่า "จ่ายแล้ว"** เงื่อนไขจึงมีแค่
  `payroll_run_id is null` ซึ่งถูก 100% ในโลกใบเก่า · วันที่ความหมายของแถวแตกเป็นสองชนิด
  เงื่อนไขเดิมกลายเป็นเท็จโดยไม่มีบรรทัดไหนเปลี่ยนเลยสักบรรทัด
- **หลักฐาน:** ห้าที่ที่ต้องเติม `and status = 'approved'` — `employee_balance` ·
  `payroll_balances` · `close_payroll_run` (**ทั้งยอดที่หักและคิว FIFO**) · `report_summary`
  · `report_labor` · ถ้าพลาดที่ `close_payroll_run`: คนงานที่มีค่าแรง ฿1,000 และมีคำขอค้าง
  ฿900 จะถูกหักคืน ฿900 **สำหรับเงินที่ยังไม่เคยได้รับ** และใบคำขอถูกตีตราว่า "หักแล้ว"
  ในทรานแซกชันเดียวกัน — ไม่มี error ที่ไหน ทุกยอดบนจอยังดูสมเหตุสมผล
- **กฎกันซ้ำ:** ก่อนเพิ่มค่าใหม่ให้คอลัมน์สถานะ ให้ `grep` หา **ชื่อตาราง** ในทุก migration
  (`from public.<table>`) ไม่ใช่ grep ชื่อฟังก์ชันที่คิดว่าเกี่ยว แล้วถามทีละที่ว่า
  *"ถ้าแถวนี้แปลว่าคำขอ ที่นี่ยังถูกอยู่ไหม"* · และ **default ของคอลัมน์สถานะต้องเป็นค่า
  ที่ปลอดภัยที่สุด** (`pending`) แล้วให้ทางที่จ่ายเงินจริงระบุ `approved` เอง
  · อย่าลืม**คนเขียนที่ไม่ใช่หน้าจอ**: ฟังก์ชัน MCP · สคริปต์ seed · สคริปต์ตรวจ
  ซึ่ง insert ผ่าน SQL/PostgREST ตรงโดยไม่เคยส่งคอลัมน์นี้มาก่อน

## ฐานข้อมูลขึ้นก่อนโค้ด = client เวอร์ชันเก่ากลายเป็นตัวเขียนข้อมูลผิดความหมาย

- **อาการ:** apply migration ที่เปลี่ยน `default` ของคอลัมน์สถานะเป็น `pending` เรียบร้อย
  ทุกแถวตรวจเขียว · แต่โค้ดที่ **ยัง deploy อยู่บน production** ไม่รู้จักคอลัมน์นี้และไม่ส่งมันมา
  → ใบเบิกที่เจ้าของเพิ่งจ่ายเงินสดออกไปจริง ๆ จะกลายเป็น "คำขอรออนุมัติ" เงียบ ๆ
  ไม่เข้ายอดเบิก ไม่ถูกหักตอนจ่ายค่าแรง
- **สาเหตุ:** "apply migration" กับ "deploy โค้ด" เป็นสองเหตุการณ์คนละเวลาเสมอ และช่วงคาบเกี่ยว
  อาจยาวเป็นชั่วโมงถ้าคนกดเมิร์จไม่ได้อยู่หน้าจอ · แผนที่คิดว่าสองอย่างนี้เกิดพร้อมกัน
  คือแผนที่มีหน้าต่างพังกว้างเท่ากับเวลาที่รอคนกด
- **หลักฐาน:** ฐานถูก apply 22 ก.ย. เวลาเช้า · main ของ repo production ยังไม่ขยับอีกหลายชั่วโมง
  · ยิงตรวจ `PATCH /api/advances/<id>` บน production ได้ **405** (เมธอดยังไม่มี) ตลอดช่วงนั้น
- **กฎกันซ้ำ:** ให้ **ฐานข้อมูลเป็นคนบังคับความหมายตาม role** ไม่ใช่ปล่อยให้ client เป็นคนส่งมา —

  **ถูกทั้งกับโค้ดเก่าและโค้ดใหม่** เสมอ แล้วลำดับ deploy จะไม่ใช่เรื่องที่ต้องลุ้น
- **เจ้าของกฎ:** `supabase-rls-schema`

## ตรวจกฎบนฐานจริงโดยไม่ทิ้งของค้าง — `do` block ที่จบด้วย `raise exception`

- **อาการ:** อยากยืนยันกฎ RLS/trigger บน **ฐานของลูกค้าที่มีข้อมูลจริง** แต่ทุกสคริปต์ตรวจ
  ที่เขียนแบบเดิม (สร้าง fixture → ยืนยัน → ลบใน `finally`) มีโค้ดเก็บกวาดที่เคยลบผิดมาแล้ว
  — บาดแผลสี่ข้อในไฟล์นี้มาจากโค้ดเก็บกวาดล้วน ๆ
- **สาเหตุ:** ทุกข้อมาจากสมมติฐานเดียวกันว่า *"ลบสิ่งที่ตัวเองสร้างได้ถูกต้องเสมอ"* ·
  แต่โค้ดเก็บกวาดคือโค้ดชิ้นเดียวที่ต้องทำงานถูกในวันที่ของอื่นพังหมด
- **กฎกันซ้ำ:** **ไม่ commit ตั้งแต่แรก** — ยัด fixture การยืนยัน และรายงานผลไว้ใน
  `do $$ … $$` ก้อนเดียว ปิดท้ายด้วย `raise exception '%', v_out;`
  · exception ม้วนทุกอย่างกลับพร้อมกัน (แถวข้อมูล · แจ้งเตือนที่ trigger สร้าง ·
  `audit_log` · รอบจ่าย) และข้อความที่ raise คือรายงานผลที่ client อ่านได้จาก error body
  · **สวมสิทธิ์เพื่อตรวจ RLS จริง:** `perform set_config('request.jwt.claims',
  json_build_object('sub', <uuid>, 'role','authenticated')::text, true)` แล้ว
  `execute 'set local role authenticated'` · `reset role` เพื่อกลับเป็น superuser
  — ไม่สลับ role เมื่อไหร่ policy ถูกข้ามทั้งหมดและสคริปต์จะเขียวโดยไม่ได้ตรวจอะไรเลย
  · 🔴 **ถ้าคำสั่งสำเร็จแทนที่จะโยน exception ให้ถือว่าแดง** เพราะแปลว่ารายงานไม่ถูกส่งกลับ
  และอาจมีของค้างจริง
- **หลักฐาน:** `scripts/verify-advance-db.mjs` — 25 แถวบนฐานลูกค้า (22 ก.ย. 2569)
  · ตรวจของค้างหลังรัน = **0 ทุกตารางรวม `audit_log`** · fixture ที่ต้องยื่นคำขอ **ต้องยื่น
  ในฐานะ role ที่ยื่นจริง** ไม่ใช่ insert ใต้สิทธิ์เจ้าของ ไม่งั้น guard จะดันเป็น `approved`
  แล้วแถวตรวจจะวัดคนละเรื่องโดยที่ตัวเลขยังดูสมเหตุสมผล (เจอจริง 4 แถวพร้อมกัน)
- **เจ้าของกฎ:** `kp-testing-cadence`

## "เมิร์จแล้ว" ไม่ใช่ "ขึ้นแล้ว" — และ repo ที่ชื่อเหมือนกันสองตัวทำให้เมิร์จถูกที่ผิดตัว

- **อาการ:** เจ้าของแจ้งว่าเมิร์จเข้า main แล้ว · แต่ production ยังเป็นโค้ดเก่าอยู่
  และ `main` ของ repo ที่ agent push ไว้ก็ยังไม่ขยับ
- **สาเหตุ:** โปรเจ็คมี repo ชื่อเดียวกันสองตัว (`<org>/<repo>` กับ `<user>/<repo>` ที่เป็น fork
  ของกันและกัน) · หน้า *Comparing changes* ของ GitHub ตั้ง base เป็น **upstream** ให้อัตโนมัติ
  คนกดจึงเมิร์จเข้าตัวที่ไม่ได้ต่อกับ Vercel โดยหน้าจอไม่ได้บอกอะไรผิดเลยสักคำ
- **หลักฐาน:** `git ls-remote <upstream> refs/heads/main` = `ea49418` (มีงานครบ) ·
  `git ls-remote <production repo> refs/heads/main` = `226cef2` (ตัวเก่า)
  · ยิง `PATCH` ใส่ endpoint ที่**มีเฉพาะในโค้ดใหม่**: production ตอบ **405** = ยังเก่า
  → หลัง deploy จริงตอบ **401 `{"error":"UNAUTHENTICATED"}"`**
- **กฎกันซ้ำ:** นิยามของ "เสร็จ" ต้องเป็น **สัญญาณที่ production เป็นคนตอบ** ไม่ใช่การกดเมิร์จ
  · เลือก endpoint หรือเส้นทางที่ **มีเฉพาะในโค้ดใหม่** ไว้เป็นตัววัดตั้งแต่ก่อน deploy
  (เมธอดใหม่บน route เดิมคือของที่ดีที่สุด: เก่า = 405 · ใหม่ = 401/200 ต่างกันชัดและไม่ต้องล็อกอิน)
  · และตอนตรวจ ให้ถามก่อนเสมอว่า **repo ไหนคือตัวที่ deploy** — `git ls-remote` ของทั้งสองตัว
  ใช้เวลาสองวินาทีและตัดความเข้าใจผิดทิ้งได้ทั้งก้อน
- **เจ้าของกฎ:** `kp-autonomous-loop`

## บังคับให้เลือกสิ่งที่ระบบไม่ได้ใช้คำตอบ — ช่องที่ถามเพื่อถาม

- **อาการ:** ลูกค้าใช้จริงวันแรกแล้วแจ้งทันที: *"เมื่อหัวหน้างานเบิกเงิน มันให้เลือกโครงการ
  ทั้ง ๆ ที่ถ้าเจ้าของเบิกเองมันไม่มีให้เลือก"* · หัวหน้าโครงการต้องเดาทุกครั้งว่าจะลง
  โครงการไหน ทั้งที่เดาผิดก็ไม่มีอะไรเปลี่ยน
- **สาเหตุ:** ตอนออกแบบ เอา **"ขอบเขตสิทธิ์ของ role"** (หัวหน้าโครงการเห็นเฉพาะโครงการ
  ที่ดูแล) มาปนกับ **"มิติของข้อมูล"** (เงินก้อนนี้เป็นของโครงการไหน) · แต่เบิกล่วงหน้า
  เป็น**เงินสดออกของคน** ไม่ใช่ต้นทุนของโครงการ — ทุกสูตรที่คิดยอดเบิก
  (`employee_balance` · `payroll_balances` · `close_payroll_run`) **ไม่มีมิติโครงการเลย
  สักตัวตั้งแต่วันแรก** · ช่องที่บังคับให้กรอกจึงไม่เคยมีใครอ่านค่าของมัน
- **หลักฐาน:** ฝั่งเจ้าของไม่เคยมีช่องนี้มาตั้งแต่ P5 และทุกอย่างทำงานถูกต้องมาตลอด —
  ความไม่สมมาตรนี้คือสัญญาณที่อยู่ตรงหน้ามาตั้งแต่แรกแต่ไม่มีใครถาม
- **กฎกันซ้ำ:** ก่อนทำช่องกรอกให้ **บังคับ** ให้ถามว่า *"ถ้าผู้ใช้กรอกผิด ตัวเลขไหน
  บนจอจะเปลี่ยน"* — ตอบไม่ได้แปลว่ามันไม่ใช่ข้อมูล มันคือภาระ · และ **ขอบเขตสิทธิ์
  ไม่จำเป็นต้องเป็นคอลัมน์ในแถว** — ที่นี่ขอบเขตที่ถูกคือ "ใบที่ตัวเองยื่น"
  (`created_by = auth.uid()`) ซึ่ง policy ใช้อยู่แล้ว
- **เจ้าของกฎ:** `kp-design-brainstorm`

## "หักหนี้ทันทีที่มีรายได้เข้า" ที่ทำให้หนี้หายฟรี เพราะรายได้ก้อนนั้นยังไม่ถูกปิด

- **อาการ:** เจ้าของสั่งว่า *"เมื่อลงชื่อเข้าโครงการ ต้องหักลบยอดที่เบิกเกินไป"* ·
  วิธีที่ตรงตัวที่สุด (ลงชื่อ → `deducted_amount += ค่าแรงวันนั้น`) ทำให้ **บริษัทเสียเงิน
  เท่าค่าแรงวันนั้นทุกครั้ง** โดยไม่มี error และยอดบนจอยังดูสมเหตุสมผล
- **สาเหตุ:** สูตรคงเหลือคือ `ค่าแรงที่ยังไม่จ่าย − เบิกที่ยังไม่ถูกหัก` · ค่าแรงวันที่เพิ่งลงชื่อ
  **ยังอยู่ในพจน์แรก** (ยังไม่ถูกตีตราว่าจ่ายแล้ว) · ไปลดพจน์ที่สองด้วยก้อนเดียวกันอีก
  เท่ากับใช้เงินก้อนเดียวสองครั้ง
- **หลักฐาน:** หนี้ ฿2,000 · ลงชื่อได้ ฿500 → ถูกต้อง −฿1,500 · แบบหักทันที −฿1,000
  · ส่วนต่าง ฿500 คือเงินที่บริษัทไม่มีวันได้คืนและไม่มีที่ไหนฟ้อง
- **กฎกันซ้ำ:** การหักกลบต้องเกิด **คู่กับการปิดยอดฝั่งรายได้เสมอ** — ถ้าจะหักตอนลงชื่อ
  ต้องตีตราวันนั้นว่า "จ่ายแล้วด้วยการหักหนี้" ไปพร้อมกัน (ซึ่งแลกมาด้วยการล็อกวันนั้น
  ไม่ให้แก้ย้อนหลัง) · ถ้าไม่ยอมล็อก ก็ต้องหักตอนจ่ายจริงเท่านั้น แล้วให้หน้าจอแสดง
  **ยอดติดลบที่ลดลงเองตามค่าแรงที่เกิด** ซึ่งสูตรเดิมให้คำตอบถูกอยู่แล้ว
  · เลือกทางหลังเมื่อ 22 ก.ย. 2569 (เจ้าของตัดสินใจเอง หลังเห็นผลของทั้งสองทางเป็นตัวเลข)
  · แถวที่กันไว้: `R14-DB-26` ต้องยืนยัน **สองอย่างพร้อมกัน** — ยอดติดลบลดลง *และ*
  `deducted_amount` ยังเป็น 0 · ยืนยันอย่างเดียวจะเขียวทั้งสองทางเลือก
- **เจ้าของกฎ:** `supabase-rls-schema`
